# S8 unit-test Skill 需求

> 你现在是一位资深嵌入式开发专家，请帮我编写一个 AI Agent Skill。
>
> 本文定义 S8 目标需求。首版已实现主机编译运行与项目示例实测；尚未完成的扩展项在文中明确指出。

## 基本信息

| 项目 | 约定 |
|---|---|
| Skill 名称 | `unit-test`（S8，名称待实现时核对） |
| 测试对象 | S5a/S5b/S5c 产生的**软件程序单元**，如函数、状态机或边界清楚的模块；不把整机功能直接当作单元 |
| 目标 | 验证给定输入和外部接口行为时，程序单元的输出、状态变化与接口调用符合已确认的预期 |
| 执行方式 | 规则层先建立候选单元清单并按配置选取范围；Agent 只处理本轮选中单元的用例与 Mock；规则脚本编译运行、收集和校验结果 |
| 触发时机 | S5 代码就位后，由用户要求或未来 S12 编排触发；S5 `code-fix` 后可以只重测受影响单元，再按需回归 |
| 首期范围 | 在开发主机运行 C 单元测试。测试代码与固件代码分离，不烧录开发板，不占用串口 |

S8 侧重“这一段代码在这些条件下是否按约定工作”。S7b 负责目标工程能否编译；S9/S10/S11 负责烧录、采集和整理实机证据。这几类结果可以互相引用，但不能互相代替。

## 输入

### 从项目级 `config.json` 读取

下列 `s8.*` 字段已加入 `schemas/config.schema.json`；CLI 可单次覆盖，不回写配置。

| 字段 | 取值 / 缺省 | 用途 |
|---|---|---|
| `s8.selection.mode` | `budget` / `ratio` / `explicit` / `changed` / `all`；缺省 `budget` | 控制本轮选择方式 |
| `s8.selection.critical_units` | 单元 ID 数组，缺省空 | 各模式下优先选择的关键单元 |
| `s8.selection.units` | 单元 ID 数组；`explicit` 模式必填 | 用户直接指定测试范围 |
| `s8.selection.ratio` | `(0, 1]`；`ratio` 模式必填 | 单元选取比例，如 `0.10` 表示 10% |
| `s8.selection.max_agent_units` | 正整数，所有模式缺省 20 | 每批最多新增/更新多少个单元的测试代码 |
| `s8.host_compiler` | 可选路径或命令 | 主机 C 编译器 |
| `s8.test_timeout_seconds` | 正整数，缺省 60 | 测试程序运行超时 |

```json
{
  "s8": {
    "selection": {
      "mode": "ratio",
      "ratio": 0.10,
      "critical_units": ["sensor_process", "protocol_decode"],
      "max_agent_units": 30
    }
  }
}
```

### 候选单元清单与范围收敛

规则层扫描源码、已有测试计划和变更记录，形成带稳定 ID、源码位置、可测性及不确定标记的**候选单元清单**；Agent 只复核本轮选中单元。规则扫描不能理解全部业务边界，无法准确拆分时应标 `inventory_uncertain`，不能给出伪精确比例。

| 模式 | 本轮选取方式 |
|---|---|
| `budget` | 先关键单元，再变更/高风险单元，最后按稳定 ID 补足；缺省每批最多由 Agent 处理 20 个 |
| `ratio` | 首版从已识别源码模块候选中取 `ceil(候选总数 × ratio)`；关键单元先占名额，数量超过比例名额仍保留；分母标为 provisional，待 Agent 复核可测性 |
| `explicit` | 选用户指定 ID 与关键单元；未知 ID 报配置错误 |
| `changed` | 首版通过 `--baseline` 指向旧清单，按源码 SHA256 变化选单元与关键单元；契约文件变化追踪留作后续扩展；没有基线则报错 |
| `all` | 选择全部已识别源码模块候选；可按 Agent 上限分批，不能主机测试的模块单独标记 |

**首版选取比例 = 本轮计划选中的源码模块候选数 ÷ 已识别源码模块候选总数**。它只是工作范围比例，不是准确的可测单元覆盖率、代码覆盖率、用例通过率或产品验收率。Agent 上限小于计划选中数量时，只处理当前批次；其余单元标为延期。关键单元多于上限时也分批，不绕过上限，更不能声称“关键单元全部通过”。首版排序依据为关键、源码 SHA256 变更、稳定 ID；已有测试自动越过 Agent 上限重跑属于后续优化。

报告必须同时给出**候选总数、暂定选择分母、计划选中数、实际完成数、延期数、未选数**。例如 1000 个源码模块候选、`ratio=0.10` 时计划选 100 个；若 `max_agent_units=30` 且没有现成测试，本批最多完成 30 个，另外 70 个标延期，不能把 100 个写成已测或声称 10% 的代码已经验证。

### 必需输入

- 项目 `config.json`，至少能定位目标工程；支持显式指定 `--target` 覆盖本次目标。
- 待测源码与头文件，以及可定位的测试计划/用例代码。
- 主机可用的 C 编译器和测试运行器；工具路径可以来自配置或显式 CLI 参数，缺失时明确报错，不默默换工具。

### 可选输入

- S2 `spec.json`、未来的 `acceptance_criteria.json`、S5 输出的模块清单/接口契约/流程图、调试反馈文档。
- `--mode`、`--ratio`、`--units`、`--critical-units`、`--max-agent-units`：单次覆盖配置中的选取策略；`--cases` 可进一步限定已选单元中的用例。
- `--run-id` 或等价选项：复查指定历史运行；新运行默认生成唯一 ID，不覆盖历史结果。

配置 Schema 已约束字段类型和模式必填参数，脚本进一步检查单元 ID 与基线。项目配置可不含 `s8`，使用 `budget` 缺省策略。

## 输出与状态

`unit_inventory.json` 记录候选 ID、位置、可测性与不确定项；`selection.json` 记录生效配置、CLI 覆盖、选择模式、分母、请求/实际选取比例、已选/延期/未选 ID 及原因。`result.json` 至少记录运行 ID、目标工程、选中/执行用例数、通过/失败/跳过/待确认/不可主机测试数、编译与运行状态、各用例结果、关联日志路径和源码快照。上述 JSON 都要定义 Schema。`report.md` 用相同事实给出摘要、失败证据、实际测试范围和未验证范围。

若项目约定使用 `state.json`，S8 只更新 `s8` 字段：`status`（`done` / `partial` / `failed` / `blocked`）、`run_id`、`result_path`、`report_path`、选中/执行/延期单元数、各用例状态计数和 `updated_at`。`done` 表示本批选中模块都有可执行用例且通过；`partial` 表示至少一个模块通过，但其他选中模块仍缺测试计划、预期或无法主机测试。两者都不表示整个产品或所有模块已验证。计划中存在延期、未选、待确认/不可测试项时仍需在报告中显著列出。`failed` 表示编译、运行或断言失败；`blocked` 表示缺少必要输入或工具，或没有任何可执行用例，因而没有有效执行。实现时应为这些字段提供 Schema，并保证失败时也保留可用日志。

S8 报告要写明“本次验证的是哪些代码版本、哪些用例”，否则 S5 后续改动会让旧结果失去对应关系。允许重跑旧用例，但新运行不得篡改旧结果。

## 文件位置

以 `<project>` 表示项目目录，以 `<build_target>` 表示 `App` 或 `BootLoader` 等目标工程。首期建议：

```text
<project>/
└── <build_target>/
    ├── App/、Drivers/、Core/ ...       # S5/用户维护的生产代码
    ├── tests/
    │   └── unit/
    │       ├── test_plan.json          # S8 用例计划及预期依据
    │       ├── test_<module>.c         # 测试程序
    │       ├── mocks/                  # 可编译的 Mock 实现
    │       └── support/                # 测试框架/适配代码（按需）
    └── outputs/
        └── s8/
            └── <run_id>/
                ├── unit_inventory.json # 候选单元与可测性
                ├── selection.json      # 选择策略、分母及未选范围
                ├── run_manifest.json  # 源码、测试代码和工具版本快照
                ├── build.log          # 测试程序编译日志
                ├── test.log           # 测试运行原始输出
                ├── result.json        # 机器可读的用例结果
                └── report.md          # 人可读摘要及失败证据
```

`tests/unit/` 在目标工程内，方便随代码版本管理，但必须**独立于固件工程编译清单**；Mock 和测试入口不得进入烧录固件。`outputs/s8/` 只放运行产物和报告，不放可编译源代码。S5b 旧需求中提到的 `outputs/s5b/tests/` 与此布局不同；落地 S8 时应将可编译测试代码统一到 `tests/unit/`，并同步修正相关 S5b 文档。项目级 `PROJECT_LAYOUT.md` 若另有约定，按项目布局解析目录，但保留这些隔离原则。

## 执行阶段

### 阶段 A：Agent 制定/更新测试计划

1. 规则层先生成候选单元清单，并按配置形成选取清单和批次；未知 ID、非法比例、缺少可信变更基线时报配置错误。
2. Agent **只阅读本轮选中单元**的源码、头文件和预期依据，复核边界和可测性。
3. 标注哪些可直接输入、哪些需要 Mock、哪些只适合实机验证。
4. 为每个可执行用例写明输入、预期和依据；对冲突或缺失的预期标记 `needs_clarification`。
5. 在 `tests/unit/` 编写/更新测试程序与 Mock，尽量通过公开接口测试；测试代码变更单独可审查。

### 阶段 B：规则脚本准备

1. 校验项目/目标路径、测试计划、工具可用性与编译隔离。
2. 写出 `unit_inventory.json` 和 `selection.json`；校验候选分母、已选、延期、未选数量一致。
3. 记录源文件、测试文件和 Mock 文件的 SHA256，以及工具版本和本次选中用例，形成 `run_manifest.json`。
4. 创建独立运行目录；历史报告不可覆盖。

### 阶段 C：规则脚本编译与运行

1. 用主机编译器编译选中单元、测试代码及必要 Mock；保存命令、退出码和 `build.log`。
2. 编译成功才运行测试程序；设置超时并保留 `test.log`。
3. 结构化汇总每个用例的 `passed`、`failed`、`skipped`、`needs_clarification` 或 `not_testable_on_host`。编译失败、进程崩溃、超时分别记录，不能计为断言通过。

### 阶段 D：规则校验与 Agent 解读

1. 规则层核对用例总数、状态、日志路径、源码快照、选取分母和批次范围是否一致，写出 `result.json` 与 `report.md` 基本事实。
2. Agent 可在报告中补充失败现象和调查线索，引用用例 ID、日志位置及预期依据；区分测试事实与推测。
3. 无法执行的用例明确说明原因和建议的下一种验证方式，不计入通过率分母。

规则脚本可以生成目录、运行命令和结果格式，**不能仅凭 S5 代码自动生成可信的测试语义或正确答案**。

## 使用方法

```bash
# 缺省 budget 模式，最多为 20 个单元新增/更新测试
python skills/unit-test/scripts/prepare.py --config examples/<project>/config.json

# 本轮选择 10% 的源码模块候选，关键单元优先；必要时分批
python skills/unit-test/scripts/prepare.py --config examples/<project>/config.json --mode ratio --ratio 0.10 --critical-units sensor_process,protocol_decode

# Agent 完成当前批次的测试代码后，编译、运行并校验
python skills/unit-test/scripts/run.py --config examples/<project>/config.json --run-dir examples/<project>/App/outputs/s8/<run_id>
python skills/unit-test/scripts/validate.py --config examples/<project>/config.json --run-dir examples/<project>/App/outputs/s8/<run_id>
```

`prepare.py` 会输出真实运行目录。`changed` 模式需额外传入 `--baseline <旧unit_inventory.json>`。

## 依赖

- Python 3.10+、`jsonschema`、主机 C 编译器和明确选定的测试框架/运行器。
- 不要求开发板、烧录器、串口、真实传感器或 S7b 构建产物。
- 首期工具组合和 Windows/Linux 支持顺序在实施前明确，运行时记录工具版本。

## 退出码

| 代码 | 含义 |
|---|---|
| `0` | 本批选中模块均有可执行用例且通过；未选范围仍在报告中 |
| `1` | 编译、运行、断言或结果校验失败 |
| `2` | 配置/输入错误、工具缺失、未知单元 ID、无可信变更基线等 |
| `3` | 部分完成：有用例通过，但本批仍有模块未完成测试 |

## Agent 参与与禁止事项

- Agent 只处理本批选中单元及直接依赖；不能为满足比例偷偷扩展到整个项目。
- 不根据当前实现推断它必然正确；预期缺失则标待确认。
- 不把选取比例写成覆盖率或通过率，不把延期、未选、跳过项目算作通过。
- 不修改 `config.json`、其他 Skill 的 state 字段或生产代码；不把测试代码加入固件编译清单。
- S8 只提供证据，用户明确要求修复后，Agent 才按 S5 维护分支处理。

## 与其他 Skill 的关系及职责边界

### 上游

1. 读取项目级 `config.json`，确定项目根目录、`project.build_target`、架构和目标源码范围。
2. 读取 S5 的实际源代码、头文件、接口契约与可用设计材料；按需要读取 S2 `spec.json`、S5 设计输入、模块流程图和调试反馈文档。
3. 若未来 S2 生成 `acceptance_criteria.json`，可作为附加输入。**首期不得要求该文件存在**；当前 S2 文档将其列为后续扩展。
4. S7b 编译成功不是主机单元测试的前置条件；S8 自己的测试编译必须通过。项目源码尚未就位、接口无法确定时，报告 `blocked`，不得伪造通过结果。

### 下游

- 输出可定位的失败证据，供用户或 Agent 结合反馈和源码判断是否需要 S5 `code-fix`、`diff` 或 `full`。
- S8 **不自动修改生产代码，不自行选择并触发 S5 修复分支**。用户明确要求修复后，Agent 再按现有 S5 分支流程处理。
- S8 完成也不自动触发 S7b/S9/S10/S11；未来 S12 可按工作流显式编排。

### 测试边界

| 能验证 | 不能据此声称已验证 |
|---|---|
| 日期计算、数值处理、状态转换、协议解析、错误码传播、重试与超时分支、对接口的调用方式 | 真实传感器精度、接线、电平、总线时序、实际中断/RTOS 调度、烧录后整机行为 |

对于强依赖 MCU 寄存器、启动流程或厂商 HAL 的代码，先判断能否隔离出可在主机编译的逻辑或替换依赖。不能隔离时列入 `not_testable_on_host`，说明原因和建议的实机验证路径；不能为追求通过率而改写生产逻辑。

## 测试单元划分原则

测试单元按**可观察行为和依赖边界**划分，不机械要求每个源文件对应一个测试文件。

1. 优先选择有稳定输入输出的纯函数，例如日期计算、校验和、范围判断。
2. 对有内部状态的模块，围绕公开接口或明确的模块行为测试状态转换，不依赖私有变量布局。
3. 对通过 Port、驱动、时钟或存储接口取值的模块，保留被测逻辑，替换外部接口并验证结果及必要的调用行为。
4. S5a 的硬件初始化与 S5c 的平台适配代码，只测试能在主机侧独立验证的参数映射、调用序列或错误处理；寄存器效果和时序留给目标机验证。
5. 单元过大、同时依赖多个真实外设时，先记录测试障碍，再在授权的代码改进流程中考虑拆分；S8 不擅自重构生产代码。

每个单元在测试计划中记录源文件、公开入口、依赖接口、预期依据、测试场景和是否适合主机执行。S5 的模块清单与追踪矩阵可帮助定位候选单元，但用例不能只由文件名或当前代码分支自动推断。

## 预期行为与用例设计

测试断言必须来自**用户已确认的需求或行为、设计契约、接口说明、标准算法或可独立计算的期望值**。代码负责告诉 S8 怎么调用；不能把当前实现直接当成正确答案。

每个用例至少包括：

| 字段 | 内容 |
|---|---|
| 用例 ID 与名称 | 稳定且能指向行为，如 `date_leap_day` |
| 测试单元 | 入口函数/模块及源文件 |
| 预期依据 | 对应需求、设计输入、接口契约或用户确认记录的引用 |
| 输入与前置状态 | 参数、初始状态、必要的 Mock 配置 |
| 操作 | 调用公开入口及次数 |
| 预期输出 | 返回值、输出参数、状态变化、必要的外部接口调用 |
| 覆盖意图 | 正常、边界、异常、恢复或回归中的一种或多种 |

优先覆盖正常值、边界值、无效输入、依赖失败、超时和恢复路径；不为凑覆盖率编造业务约定。若预期有冲突或缺失，把用例标为 `needs_clarification`，保留候选场景与问题，不执行含糊断言。此时其他预期明确的用例仍可运行。

## Mock 的使用规则

Mock 是测试侧的替代接口实现，可返回预设值、模拟失败/超时，并记录调用次数或参数。它应替换**被测代码调用的外部接口**，而不是替换被测逻辑本身。

```text
输入直接作为参数传入 ──→ 测试程序直接给值 ──→ 调用被测单元 ──→ 断言
被测单元从接口取值 ──→ Mock 配置该接口 ──→ 调用被测单元 ──→ 断言
```

Mock 不负责“生成测试日志”。测试运行器记录用例执行与断言结果，Mock 只提供受控行为及可检查的交互记录。已有 S5b 可选 Mock 产物若存在，可以评估复用，但 S8 不假定其完整、可直接编译或符合本次用例。S8 可自行在测试代码目录建立 Mock，且不得把可编译 Mock 代码放入 `outputs/`。

### 传感器模块例子

假设 `sensor_process()` 调用 `sensor_read()`：

| 场景 | Mock `sensor_read()` | 断言示例 |
|---|---|---|
| 正常读取 | 返回成功与 25°C、60% | 数据有效，数值按契约保存/输出 |
| 读取失败 | 返回错误码 | 状态/错误码按契约变化，不使用旧值冒充新数据 |
| 超时后恢复 | 先超时，再成功 | 第一次报告故障；第二次恢复行为符合契约 |

只有契约明确要求时才断言调用次数、重试次数或故障标志的具体值。若真实传感器未连接，主机测试仍可验证处理逻辑；实机通信是否正常需另行验证。

### 星期计算例子

- 若接口是 `calc_week_value(year, month, day)`，直接传入 `2024-02-29`，预期星期四；传入 `2000-01-01`，预期星期六。此时不需要 Mock。
- 若函数内部调用 `get_current_date()`，用 Mock 让该接口返回 `2024-02-29`，再检查结果为星期四。
- 非法日期（如 2 月 30 日）的预期错误行为应由函数契约确定，不能凭测试作者猜测。

## 验收标准

| 场景 | 期望证据 |
|---|---|
| 纯函数正常与边界输入 | 星期计算的已知日期直接输入，通过/失败逐用例可查 |
| 外部接口正常与失败 | 传感器读取 Mock 分别返回成功、错误/超时，处理逻辑断言可查 |
| 生产代码引入缺陷 | 至少一个用例失败，报告指向实际/预期差异与日志位置；恢复代码后重测通过 |
| 测试编译失败或工具缺失 | 明确 `failed`/`blocked`，保留编译日志或错误说明，不出现“全部通过” |
| 预期不明确 | 用例标 `needs_clarification`，其他独立用例仍可运行，不猜测结果 |
| 编译隔离 | S7b 固件工程不包含 `tests/unit/` 和 Mock 的可编译源文件 |
| 大项目范围收敛 | 1000 个候选可测单元、10% 比例时显示选取分母与 100 个计划单元；Agent 上限 30 时另列本批完成和 70 个延期单元 |
| 关键单元与指定范围 | 关键单元优先；未知 ID、非法比例或 `changed` 模式无可信基线时明确报错 |

首期至少用一个无需 Mock 的单元和一个需要 Mock 的单元完成实测。实测闭环包括：设计用例、编译运行、观察一次故意引入的失败、恢复后重测、核对报告与 `state.s8`、确认固件编译清单未混入测试代码。若某具体项目没有真实传感器或日期模块，可选择同类型单元替代，保持两类测试路径都得到验证。

## 实施时必须同步的全局契约

- 在 `schemas/config.schema.json` 增加并校验 `s8.*` 字段。
- 在 `docs/PROJECT_LAYOUT.md` 补充 `tests/unit/`、`outputs/s8/` 和固件编译排除规则。
- 修正 S5b 文档中将可编译测试/Mock 放入 `outputs/s5b/` 的旧描述。
- 为单元清单、选择记录、结果及 `state.s8` 定义 Schema，并提供大项目分批选择样例。
## 后续实现时需明确的选择

1. 主机 C 测试框架与编译器的首期组合，以及 Windows/Linux 的支持顺序。
2. `test_plan.json`、`result.json` 和 `state.s8` 的正式 Schema。
3. 依赖很重的模块采用编译桩、链接替换还是源代码依赖注入；按模块选择，不全局强制一种技术。
4. 代码覆盖率工具是否加入首期。覆盖率只能说明代码被执行，不能代替正确断言；首期不以覆盖率百分比作为通过条件。
5. S12 将来如何调度 S8，以及 S5 修改后的受影响用例选择规则。
