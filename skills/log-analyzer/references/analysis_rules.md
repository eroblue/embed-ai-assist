# S11 分析规则

## 要整理的内容

- **错误/告警**：保留日志中的级别、错误码、原文和位置。只说日志报告了什么，不解释根因。
- **关键运行流程**：记录明确出现的启动、初始化、外设就绪、请求/响应、任务开始/完成和状态转换。只有日志明示成功，或明确对应的请求和响应都出现时，才使用“成功/完成”。
- **重复现象**：报告完全相同记录的出现次数和代表性 evidence ID。重复心跳或周期数据可以是运行现象，不自动认定为故障。
- **事件顺序**：按同一来源中的记录顺序描述。S10 时间戳标为主机接收时间；不确定时间戳语义时不做精确时间推断。
- **缺失事件**：只有用户明确提供预期事件及观察范围时才检查。写作“在指定输入/范围内未找到”，不写“设备没有执行”。

## 事实和不确定性

1. 每条 finding 都要在 `analysis.json` 中引用一个或多个有效 `evidence_id`。
2. 区分日志事实、重复记录归纳、用户观察和无法确认的事项。
3. 如果日志为空、不能解码或没有可识别事件，明确写出；不要补造正常流程或故障。
4. 如果 S10 会话元数据表明采集较晚开始、提前停止或异常结束，在报告中说明可见的采集窗口和限制。没有元数据就写未知。
5. 用户没有给出预期行为或合法值域时，不判断功能是否符合需求，也不自行设置阈值。

## `analysis.json`

- `summary`：一两句概括最重要的可观察结果；无可确认事件时说明这一点。
- `user_observation`：用户提供的描述；没有则为 `null`。
- `findings`：按日志事实写结论，类型使用 schema 中的枚举值。
- `limitations`：采集窗口、解码或时间信息带来的限制；没有则空数组。
- 不添加根因、代码 owner、修复方案或自动路由字段。

## `report.md`

使用精简结构：

1. **结论摘要**：日志能确认的主要现象。
2. **运行流程**：按记录顺序列出关键流程节点；没有明确节点则说明。
3. **错误与重复现象**：有则列出次数、原文位置和 evidence ID；没有错误时明确写“未发现明确错误记录”。
4. **证据与限制**：说明采集窗口/停止情况及尚不能确认的内容。

引用使用 `` `SRC01-L000123` `` 形式。原始路径和行号可从 `source_index.json` 查到。不要把大段日志复制进报告。
