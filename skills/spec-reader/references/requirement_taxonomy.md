# 需求分类与优先级规范

> `requirements[]` 的 category / priority 判定标准，以及 S2 与 S5b 的
> 职责边界（越界判定）。

## 1. category 四枚举

### functional（默认）

功能行为：产品"做什么"。

- "每 2 秒采集温湿度"、"本地 LCD 显示当前值"、"按键切换模式"
- 判断：删掉它产品少一个能力 → functional

### interface

功能级接口/外设需求：产品"需要什么通信/交互能力"——**是需要什么，
不是怎么连**。

- "需要串口与上位机通信"、"WiFi 数据上报云端"、"蜂鸣器告警提示"
- 允许：通信对象、方向、内容级语义（上报环境数据）
- **禁止**：波特率、帧格式、命令码、校验方式、引脚号、DMA——归 S5b
  设计输入

判断技巧：描述里有"与 XX 通信/连接/上报/接收"→ interface；
描述里有具体电气/协议参数 → 越界，剥掉参数留能力，参数不登记。

### performance

性能指标：产品"做到什么程度"的可量化要求。

- "按键响应时间 ≤ 100ms"、"温度测量精度 ±0.5℃"、"告警上报延迟 ≤ 1s"
- 判断：带可量化数字（时间/精度/吞吐量/成功率）且描述行为质量 → performance
- 采集周期这类"业务节拍"归 functional（同时登记 business_timing），
  响应延迟这类"质量要求"归 performance

### constraint

系统级约束：产品运行的前提性限制。

- "不使用动态内存"、"7×24h 连续可用"、"上电 3s 内进入工作状态"
- 判断：全局性前提/限制，不是某个功能点 → constraint

一条需求同时符合多个类别的处理：按**主要属性**归类一次，不重复登记。
如"上电 3s 内就绪"（启动时间约束）→ constraint；
"按键响应 ≤100ms"（交互质量）→ performance。

## 2. priority 三级

| 级别 | 含义 | 判定信号 |
|---|---|---|
| must | 必须实现，缺失即验收不通过 | 规格书正文明确要求；核心能力 |
| should | 应当实现，可协商取舍 | "建议/最好/优先"措辞；增强能力 |
| could | 可选增强，资源允许才做 | "可选/若支持/扩展"措辞 |

规格书未标注优先级时：核心功能点（采集/显示/控制等主链路）判 must，
辅助能力（指示、日志等）判 should；不确定时从 must 起评，宁可保守。

## 3. S2 与 S5b 的职责边界（越界判定）

**S2 管"产品要什么"（需求侧），S5b 管"技术上怎么实现"（设计侧）。**

| 内容 | 提取方 |
|---|---|
| 功能清单、业务状态、业务时序、错误策略、数据项、阈值范围 | **S2** |
| 帧格式、命令码、波特率、校验方式、引脚映射、DMA、外设选择、消抖/调度/心跳实现 | **S5b**（s5b_design_input.md） |
| 模块拆分（module_list.json）、流程图、Port 接口、C 代码 | **S5b** |

典型越界示例（错误写法 → 正确处理）：

- ✗ description: "通过 USART1（PA9/PA10，115200-8N1）上报数据"
  ✓ REQ: "向上位机上报环境数据"（category=interface）；
    引脚/波特率细节不登记任何字段
- ✗ acceptance: "使用 TIM3 消抖后按键稳定响应"
  ✓ REQ: "按键切换工作模式，响应时间 ≤100ms"（消抖实现归 S5b）

## 4. REQ 粒度示例（SmartEnvGuard）

12 条 REQ 的拆分示范（REQ = 可独立验收的功能点）：

- REQ-001 环境数据周期采集与保存（合并"采集频率"+"数据保存"）
- REQ-002 采集失败处理（合并"保留旧值"+"连续失败告警"+"恢复"）
- REQ-005 自动控制逻辑（合并"自动/手动"+"阈值告警"+"蜂鸣"+"恢复"）
- REQ-012 数据有效范围与系统级约束（合并"范围"+"无动态内存"+"24h 可用"）

中等复杂度项目典型 10~20 条；超出 30 条说明粒度过细（回到"每句话一条"）。
